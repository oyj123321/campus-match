# 管理员分析

入口 `/admin#matching-analysis`，沿用管理员登录与不缓存策略。

## 每轮匹配

完整批次 `run_batch_all` 自动生成报告，按轮次开始时的参与池与候选规则诊断，完成后记录成功分配的人数。跨校和校内合并去重；即时匹配不计作完整批次。失败轮次可能已有部分配对，不能当作零成功。

轮次报告仅保存汇总数字和学校汇总，不保存参与者 ID、答卷、联系方式或个人诊断。所有轮次保存在数据库中，后台按最近 30、90 或 365 天查询最多 100 轮，趋势展示最近 20 个有数据的完成轮次。旧轮次不补算；旧报告没有的学校细分指标显示为未记录。

- 匹配率 = 配上人数 / 参与人数，不是配对条数 / 人数。
- 原因按未匹配者互斥分类，合计等于未配上人数。“仅放宽某条件”表示其他规则满足时能够出现候选，不保证分配成功。
- 无候选、一个候选、至少两个候选覆盖所有参与者。
- 多人共用唯一候选：至少两人都只剩同一个合适候选。统计的是这些参与者的人数。
- 历史排除后无候选：当前没有候选，但存在其他规则全部满足的历史配对对象。该人数与其他诊断可重叠，不代表建议重新配对。
- 学校筛选只统计该校参与者，候选仍来自完整参与池，保留双向跨校规则。

## 对比与自动提醒

只比较分析版本、分数门槛、跨校开关和报名要求相同的完成轮次。其他规则或人群变化仍可能影响结果；比较不代表因果。

卡片基准使用此前最多 5 轮的配上总人数 / 参与总人次，不取百分比的简单平均。下降提醒排除最近两轮另算历史基准：最近两轮及至少 3 轮历史各至少 20 人，且最近两轮都下降至少 10 个百分点才提醒。小样本、基准不足、失败、报告损坏、运行超过 60 分钟分别提示。

提醒仅显示在后台，不自动改偏好、重新匹配或发送外部消息。失败后的重跑记录为新轮次，不可视为独立的周度样本。

## 新用户漏斗

`product_journeys` 只记录上线后注册的新账号的 ID、学校和首次阶段时间；不会把老用户现在的状态伪装成历史事件。配对阶段从既有配对记录读取。已删除账号不再计入漏斗。

时间筛选限定同一批注册用户，展示他们截至现在依次达到各阶段的累计人数。学校使用注册时学校，轮次筛选不影响漏斗。隐私资料完成也计入资料完整。批次入池、预约成功或即时匹配请求成功计入参与，获得配对也可证明参与。

获取结果指接口成功返回有效配对，不代表已读、联系或交往。等待匹配的人不能直接判作流失。阶段记录不包含答卷文本或联系方式。

## 部署与维护

备份数据库后正常启动应用，`ensure_schema()` 自动创建 `matching_rounds` 与 `product_journeys`，无需额外依赖或服务。现有用户、匹配池与配对保持原规则。

分析失败会记录服务器日志，匹配继续执行。轮次报告与业务配对分开提交；进程中断可能留下运行中记录，后台会提醒核查，不自动宣称失败或重发通知。分析需要在批次开始时遍历候选对，复杂度为 O(n²)，后台查看只读已保存的汇总，不重跑候选诊断。

交互设计参考 Metabase 的筛选与下钻、PostHog 的同人群漏斗、Grafana 的持续条件提醒；未引入它们的代码或服务。
